# HomerConversations

The Chat page: the conversations an instance's **conversation proxy** (`homer-proxy`) recorded — Slack threads the connector ran a workflow in, and conversations started here — and a composer that starts or continues one the way a Slack mention does.

## Design notes

- **The proxy is per instance, with a token of its own.** `homer-proxy` fronts one Homer for the Slack connector (the connector's `HOMER_BASE_URL` points at it) and records every `POST /api/v1/agent/*` it forwards; the app talks to its API (`GET /me`, `/workflows`, `/conversations`, `/conversations/{id}`, `POST /conversations`, `POST /conversations/{id}/messages`, `GET /events`) with a Bearer token the proxy's config lists under a client name, which is the author of what is sent from here. The token has nothing to do with the Homer session: signing out of Homer keeps it, and a proxy that refuses it (401) is never a Homer sign-out — the reducer's `Delegate` has only `openProcess`, by design, and a 401 from any call (`failed(_:_:report:)`) puts the connect form in the page's place with a note (`proxyRejected`). The settings live in `homerProxies.json` beside the sessions, `0600`, keyed by the instance's base URL (`HomerProxySettingsStore` in `HomerCore`, behind `HomerProxySettingsClient`) — not `@Shared(.fileStorage)`, which cannot set a file's permissions, and the token is a secret. They are read on every `shown`, saved by a successful `/me`, removed by Disconnect and when the console forgets the instance
- **Its own requests** (`HomerProxyAPI`): another host, Bearer rather than cookies, so not `HomerAPI.send` — but the same status check (`HomerAPI.check`, with `refusalsInServerWords` so a 404 or 502 carries the proxy's `msg`), `decode`, and the event-stream reader (`HomerAPI.events(request:session:onResponse:)`, lifted out of the Homer streams for this). One `URLSession` per proxy URL, with no cookies, as `HomerAPI` keeps one per instance. Timestamps are epoch seconds as everywhere; unknown origins, roles and run states decode as `.unknown`, so a newer proxy keeps working. A run's `State` is the proxy's (`queued`, `running`, `waitingResume`, `finished`, …, `parked`, `timeout`, `error`); the ones that are a Homer status map onto `HomerProcessStatus` for the shared badge (`processStatus`), the rest get a pill of their own — `HomerProcessStatus` is not widened, which would change the process list's filters
- **Live, with a poll behind it.** The page follows `GET /events` (`followEvents`) from the last event's id (`Last-Event-ID`), reconnecting with a doubling wait (1 s to 30 s) when the stream drops. `HomerProxyAPI.events` yields a `.connected` event of the app's own when the response's headers arrive, so the page knows the stream is up before anything happens; while it is down (`streamDropped`) the list and the open conversation are re-read every 10 s (`pollWhileDown`), and the next `.connected` re-reads them once more (`needsResync`) for what the proxy sent meanwhile. The proxy's `reset` event (a resume from an id it no longer holds) re-reads them too. Events are applied by id — upsert, append-if-absent — so a replayed event is harmless; a message or run of a conversation other than the open one only touches the list (through the conversation's own `conversation.updated`)
- **The list is paged by cursor** (`limit`, `cursor`, `nextCursor`), newest activity first. Load More appends the older page; a refresh and the fallback poll re-read the first page with `limit` grown to what is loaded, so every loaded row stays current, as the process list does with its `limit`. The list is a `List` (rows recycle); the open conversation is a `LazyVStack` in a `ScrollView`, which is fine on a page — it would have to be a `List` in a sheet (README: sheets have a fixed ideal size)
- **Sending** (`sendTapped`) with no conversation open starts one (`POST /conversations` with the composer's workflow command, `""` the default); with one open it continues it (`POST /conversations/{id}/messages`) — the same workflow and thread key, so the agent carries on its session; a Slack-started conversation can be continued here too, and the answer lands in the proxy only (the proxy never writes to Slack). The answer to a creation holds the conversation, its message and run, so the thread is set *before* the selection changes: `onChange(of: \.selectedConversationID)` then finds it already showing that conversation and does not re-read it. The draft is cleared on success only. `BindingReducer` sits inside the `CombineReducers` the `onChange` wraps, or a selection written by the list's binding would not be seen by it
- **Markdown** is rendered inline-only (`HomerMarkdown.inline`, shared with the questions), never loading images, for the reason the HomerFeature README gives for question text
- **The composer picks a workflow** only for a new conversation, and only when the proxy lists more than one (`picksWorkflow`); a follow-up continues the conversation's own. ⌘↩ sends; Return alone is a new line in the `TextEditor`
- **A run row** shows the proxy's state, the current command while it runs, cost and duration, and one link per process id (a parked-and-resumed run has several), which opens the run's page through `HomerPageDelegate`-style `delegate(.openProcess)` — the page already shows the status, log tail and Claude transcript, so the chat does not stream LLM events itself
