# HomerContinuations

The Continuations page: continuations and, beside them, ask-and-dispatches.

## Design notes

- **Two kinds of agent the server starts later**, on a run's behalf: a continuation (once a watched run finishes) and an ask-and-dispatch (once a question is answered). The server lists, filters, pages and cancels both the same way (`GET /continuations` and `/dispatches` with `status`, `agentName`, `limit`; `GET`/`DELETE /{id}`), so one generic list reducer serves both — `HomerRecordListReducer<Kind>`, `Kind` being `HomerContinuationKind` or `HomerDispatchKind` (their calls, their words, what the instance is told after a cancel). The records share `HomerDeferredStart` (status, agent, origin run, expiry, start time and run, error, inputs); a card and the detail sheet read them through it, plus `HomerRecordPresentation` for the chain of runs each one draws. The web console has the continuations page only (`continuations/page.tsx`); a dispatch it shows only on its question, so the dispatch list has no web counterpart — which is also why it is a section of this page rather than a page of the header's picker (the Safari button opens the current tab's web page)
- **The page** (`HomerContinuationsReducer`): a section picker (Continuations, Dispatches), each section counting its pending records once read. Only the section on screen polls: the instance's `shown`/`hidden`/`refreshTapped` reach it, and switching hides one and shows the other. The agent filter's choices are the instance's agent names, which the instance copies in (`agentNames`)
- **A list** shows what needs attention by default (`HomerRecordFilter.open`): the pending records, soonest to expire first (those without an expiry last), and those that failed to start their agent — shown only when there are any; agents report crashes through continuations, so a lost one is a report nobody gets. A pending record due within the hour (`HomerExpiry.soonWindow`) says so in orange on its card ("Expires in 12m", ticking every 30 s) and the section counts them. The status filter (All statuses, or one) turns the list into the history: one page newest first, as the server orders it, with "Showing n of m" and Load More, which grows `limit` (as the process list does) so a refresh keeps every loaded row current. Settled records are kept a week by default (`settledRetentionSec`). A filter change clears the lists and restarts the poll; an answer carries the filters it was asked with and is dropped if they changed meanwhile. One cancellable loop every 30 s, the console's cadence
- **Cancel** is offered for PENDING only and is not checked against the user's grants: the console doesn't, and the API's records have no `owner` to check (the server applies `canControl`). It asks first. Cancelling a dispatch expires its question, so the instance re-reads the open questions (`HomerPageDelegate.questionsChanged`); cancelling a continuation re-reads the page picker's count (`continuationsChanged`). A cancel always refetches, as the console does on settle; a 409 or 404 reads as "can no longer be cancelled", since the list was stale
- **The detail sheet** (`HomerRecordDetailReducer`, Details on a card or its context menu) reads the record again (`GET /continuations/{id}`, `/dispatches/{id}`), the card's copy standing in until then: the input that gets the result or answer (`resumeParam`/`answerParam`), the other inputs (masked by the server), the question's id, the times, the runs. A run link closes the sheet and opens the run's page; Cancel closes it and hands over to the list, which asks first
- A card draws the record as a chain — origin → what it waits for (the watched run, or the answer) → the agent it starts, with the run that start made once dispatched — which wraps on a narrow card; the sentence is its accessibility label. The run numbers are links in each node's `AttributedString`, with a private `homer-process:<id>` scheme (`HomerRunLink`) that the card's `openURL` action turns into `processTapped`
