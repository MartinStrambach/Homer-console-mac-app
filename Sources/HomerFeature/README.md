# HomerFeature

The console and its instances: `HomerConsoleReducer`/`HomerConsoleView`, `HomerInstanceReducer`, the process list and the questions. It composes every other module and is the package's only product.

## Design notes

- **Several instances, all signed in at once.** `HomerConsoleReducer` holds one `HomerInstanceReducer` per instance (`forEach`, so each one's effects and cancellation IDs are its own) and which one is on screen. Unlike the web console, which keeps one active instance and re-probes auth on every switch (`lib/instances/store.ts`, `instance-switcher.tsx`), every instance stays live: all check their session at launch and poll their open questions (the host's badge is the sum; the instance menu shows each one's, and the others' total beside it), and the selected one alone polls its processes, Flow cells and agent names, only while the console is on screen (`activated`/`deactivated`). Switching shows the instance's last data at once and refetches right away. The header's instance menu lists them with ⌘1…⌘9 (hidden buttons do the switching, since a closed menu does not reliably answer its items' shortcuts; selecting the instance on screen again is a no-op, so the two never fight), adds one and removes the selected one. The processes/questions tab is the console's, not an instance's, so it survives a switch
- The instance list (`@Shared(.homerInstanceURLs)`, base URLs in the order added, which is the ⌘-digit order) gains an instance only on its first successful sign-in, so a failed attempt adds nothing; adding a URL already in the list signs that instance in again (a different user's data is dropped). Signing out keeps the instance in the list, signed out; "Remove" signs it out and forgets it. The selection is `@Shared(.homerSelectedInstance)`. `HomerEndpoint.normalize` accepts a URL pasted from the browser's address bar: it assumes `https`, drops a trailing console route (`/processes/123`, `/questions`, …) and any query, and keeps a sub-path otherwise. `displayName` keeps a port and sub-path, so two instances on one host read apart
- Polling follows the console's cadences: processes every 5 s and only for the instance on screen, open questions every 30 s for every signed-in instance. Each poll is one cancellable loop that fetches immediately; a filter change or "Load more" restarts it, so an answer for the old query never lands after the new one. "Load more" grows `limit` rather than paging, so the refresh keeps every loaded row current
- The process list is a SwiftUI `Table` with the console's columns (`process-table.tsx`): ID, Agent with tag chips, Status with the open-question count, Status Time, Last Command, Cost, Runner (pod-phase dot for Kubernetes runs), Flow (Root runs view only), Purge, Actions. Values use the console's own formats (`HomerFormat`, from `lib/utils/format.ts`): `dd.MM.yy HH:mm:ss`, `$0.0000`, "in 2d 3h". The page's filters are all there too: status chips, agent, sort order, tag chips (a row's tag adds itself), and "Children of #id" (context menu ▸ Show Child Runs), which overrides the Root runs view as in the console. "Total cost" sums the listed rows, not every match, like the console's
- Kill and Retry are offered only where the console offers them: by status (`isKillable`/`isRetryable`) and by the user's grants from `/auth/me` (`HomerUser.canKill`/`canRetry`, a port of `lib/auth/use-can.ts` — admin, owner `session:<username>`, or a grant whose agent pattern matches). The server checks again. Kill asks first; a retry opens the new run's page, as the console navigates to it
- The Flow cell (`HomerFlowSummary`, from `flow-summary-cell.tsx`) summarizes the runs under a root: a count from the page's `total`, cost and an aggregate state from the newest 100 (`partial` past that). Only the first 20 rows get one — one request per cell, polled every 30 s and restarted when those rows change — so "Load more" does not multiply the requests
- **The other pages** (Continuations, Schedules, Agents, Costs — the console's sidebar, Schedules and Costs for admins only) each have a reducer scoped into `HomerInstanceReducer` (`continuations`, `agents` — Schedules is the agents with a cron, so the two pages share it — `costs`). The console sets the instance's `page`; the instance tells the matching reducer `shown`/`hidden` (`syncShownChildPage`) — only while the instance is on screen and signed in, and never an admin-only page for anyone else — and the page polls only in between. A page asks the instance for what only it can do through `HomerPageDelegate`: `.unauthorized` (a 401 signs the instance out), `.openProcess` and `.continuationsChanged`. Signing out or another user signing in hides the page on screen and replaces every page's state. Each page adds its own calls to `HomerAPI` (an extension in its own file, through `HomerAPI.send`/`decode`) and its own `@DependencyClient`, rather than growing `HomerClient`. The header's Refresh reaches the page on screen as `refreshTapped`. `HomerAPI.send` takes request headers, pre-encoded query items, and `refusalsInServerWords` for calls whose 409/429 mean something other than a question or the login limiter (an agent run)
- **The pending continuations count** (the console's sidebar badge since Homer 1.31) is the instance's, not the page's: `GET /continuations?status=PENDING&limit=1`, whose `total` counts past the page, every 30 s. Unlike the questions, it is polled only while the instance is on screen — only the page picker's "Continuations (n)" shows it. A failure keeps the last count silently (the other polls report an expired session). A cancel on the page tells the instance (`HomerPageDelegate.continuationsChanged`) to re-read it at once
- Question text is Markdown written by an agent. It is rendered inline-only (`AttributedString`, `.inlineOnlyPreservingWhitespace`), and `Text` never loads images — the console renders only an image's alt text for the same reason: an agent-supplied image URL would otherwise beacon on view
- **A run's page** (`HomerProcessDetailReducer`, `processDetail`) shows in place of whichever page opened it — Processes, Questions or a page reducer's — with Back to it, as an agent's page does inside Agents and Schedules. While it covers a page reducer's page, `syncShownChildPage` tells that reducer `hidden` and the run's page `shown`; the process list and questions are the instance's own polls and go on (the badges need them). Details in [`HomerProcessDetail`](../HomerProcessDetail/README.md)
- The instance's open questions are answered on the Questions page and on a run's page alike, both through the instance: `HomerProcessDetailView` takes a view builder for a run's questions, which the console fills with `HomerRunQuestionsView`, so the process-page module never sees `HomerInstanceReducer`
- **A run's questions** are all of them, as the console's `question-panel.tsx` lists them: `GET /questions?processId=` (no status) is the instance's `runQuestions`, polled every 30 s exactly while a run's page is on screen and read again for the run it shows — an `onChange` of `processOnScreen` catches the page opening, closing, being covered or uncovered (another page, another instance) and moving to another run (retry, sub run, Back); a covered page keeps its last list, and only another run (`processDetail?.processId`) clears it. An answered question shows its answer and what its dispatch did ("Started run #n", which opens on the same page with Back, or "Dispatch failed: …"); an expired one says the run ended first. Until the run's list arrives, its open questions from the instance's own poll stand in
- **Cancelling an ask-and-dispatch question** (`DELETE /dispatches/{id}`, only while the question is open and has a dispatch) asks first in the console's words, then expires the question so its agent never starts. The confirmation is the instance's `questionToCancel`, shown by the card it belongs to — the Questions page and a run's page each present their own. A 409 or 404 means someone answered or cancelled it first and says so; either way the questions are re-read, as the console does once the call settles
- **`/health` and `/heartbeat`.** The orphan pod sweep (`HomerSweepBanner`, `sweep-status-banner.tsx`) shows above the process list only on an instance with a Kubernetes runner, read every 60 s while that list is on screen and no run's page covers it (the console's `staleTime`). The version is read once, the first time the instance comes on screen, and shown in the account menu rather than the console's corner badge; a failure of either is silent
