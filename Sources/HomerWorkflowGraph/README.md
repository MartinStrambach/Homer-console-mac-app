# HomerWorkflowGraph

LangGraph workflow models, the dagre-like layout, and the graph and status views.

## Design notes

- **LangGraph workflow**: `GET /processes/{id}/langgraph` without `graph` is the cheap probe (404 = no workflow), asked only when its answer is used — Resume (FAILED/KILLED/UNKNOWN runs, shown only with a workflow and a `run` grant), an expanded execution, or the running command's "Show workflow" — and asked again when a command runs that a "no workflow" answer did not see, since the workflow's artifact appears only when its command starts. The node states (`graph=true`) are polled every 5 s exactly while shown under the execution that ran the workflow or under the live command, whatever the run's status (a parked segment is FINISHED while its thread moves on). With a `topology` (Homer 1.28, ADR-0073) the workflow is drawn as its graph (see **Workflow graphs**): node boxes tinted by state, the sub runs' command dots along their bottom edge, the edges the run took green (`traversed`, Homer 1.29), and a node with sub runs opens them in a popover. Without one, or above the render cap, the nodes are the console's graph-less fallback list, in graph order (`HomerLangGraphStatus.nodes`: JSON object order does not survive decoding) — from `topology.nodes`, else from the deprecated `mermaid` source, which an older server or `homer_langgraph` runtime still sends alone (`draw_mermaid` writes nodes in graph order; ids are matched through langchain's `_to_safe_id` escaping) — drop the Mermaid path once no instance predates 1.28. The list has the legend's colors, the sub runs' command dots, and after each node the targets of the edges the run took from it. The subs list and node errors follow either. "Show Graph" (the run's console page over the sheet) is offered only for a Mermaid-only workflow, which the console can draw and this cannot
- **Workflow graphs** (`HomerGraphLayout`, `HomerWorkflowGraphView`, from `workflow-graph.tsx` and `lib/langgraph/layout.ts`). The console lays a `topology` out with dagre; there is no Swift dagre, so `HomerGraphLayout` is a native layered layout that follows dagre's conventions step by step, so the two look alike: DFS cycle breaking (reversed edges drawn the right way round), every edge spanning two ranks with its label in the odd rank between (dagre's doubled `minlen`/halved `ranksep`), longest-path ranks then moves that shorten edges (standing in for network simplex — the factory graph gets dagre's height), dummy chains, dagre's ordering loop (up sweep first, ties biased right every other two sweeps, an equally good order replacing the best, four sweeps without gain to stop — that tie rule is what spreads long edges to both sides of a chain), and Brandes–Köpf x positions. A weighted least-squares placement was tried first and dropped: layer-by-layer sweeps cannot move a long edge's dummy column as one, so chains drifted into a staircase. Self-loops, the 200-node/300-edge cap, the 40-character label cut and the spacings (`nodesep` 32, `ranksep` 44, `edgesep` 16) are `layout.ts`'s. Boxes are measured with the font they are drawn in (callout × `uiFontScale`), not estimated per character, so the layout follows the text size; it is computed off the main actor and only when the topology or scale changes, not on every 5 s status poll. Edges are a `Canvas`; nodes are views over it, for tooltips, popovers and accessibility. On the process page the graph is at most 480 pt high and scrolls inside, keeping the sheet's height fixed. "Export" (and the graph's context menu) saves or copies the whole graph as a PNG: `HomerWorkflowGraphDrawing` — the edges and boxes alone, which the screen shows with clear popover buttons laid over it, as the console lays its triggers over the SVG — rendered by `ImageRenderer` at 2× in the current appearance and text size, the bitmap's point size set so it opens at the graph's size
